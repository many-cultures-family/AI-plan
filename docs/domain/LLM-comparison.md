## 1. 이 문서가 답하려는 것

우리 서비스는 한국어 신청서를 사용자의 모국어로 풀어 주는 서비스다. "번역"이 어디에 들어가는지, 그 번역을 어떤 방식으로 만들지 세 가지를 비교한다.

| 방식 | 한 줄 설명 |
| --- | --- |
| 방식 1. 번역 API | 상용 번역 API(서버에서 호출)만으로 한국어를 모국어로 옮긴다 |
| 방식 2. 번역 API + LLM | 번역 API를 기본으로 하고, 문맥이 필요한 문장은 LLM(번역 특화 모델 `riva-translate-4b-instruct-v2` 등)이 맡는다. 서술형처럼 개인정보가 섞일 수 있는 글은 개인정보 차단 절차를 거친 뒤에만 보낸다 |
| 방식 3. 번역 API + 로컬 LLM | 서버 전송 없이 사용자 기기에서 번역한다. 1단계는 브라우저 내장 `Translator API`, 지원하지 않는 환경은 2단계 `Transformers.js`로 넘어가고, 그것도 안 되면 번역 API로 넘어간다 |

## 2. 번역이 필요한 곳 (문서에서 확인한 것)

번역이라는 한 단어 안에 성격이 다른 일이 섞여 있다. 방식을 고르기 전에 나눠 본다.

| 번호 | 번역 대상 | 어디서 나오나 (문서) | 개인정보가 섞이나 | 특징 |
| --- | --- | --- | --- | --- |
| T-A | 화면 문구, 오류 메시지 | `03` R3: 오류 메시지는 프론트엔드 국제화로 보여 준다 / 미팅1 질의응답 2 | 아니오 | 미리 번역해 파일로 두면 되므로 번역 방식 선택과 거의 무관하다 |
| T-B | 용어 사전의 설명 | `03` R5: 기본 설명은 서버 용어 사전에서 제공. 팀이 검증해 구축 | 아니오 | 한 번 번역해 저장하고 사람이 검수한다. 같은 질문에 같은 설명을 주는 것이 목적이다 |
| T-C | 입력 항목의 모국어 설명 (L1, F-02) | `03` 3-4 L1: 개인정보를 가린 OCR 텍스트와 칸 라벨을 입력으로 항목 설명을 만든다 | 마스킹이 실패하면 섞일 수 있다 | 문서마다 달라서 실행 때 번역해야 한다 |
| T-D | 모국어 쉬운 풀이 (L2, F-05) | `03` R5: 사용자가 '이해하지 못함'을 고를 때만 LLM이 만든다 | 입력은 단어·문장·사전 설명뿐 (사용자 값 없음) | 번역보다 쉬운 말로 바꾸기에 가깝다 |
| T-E | 서술형 답변 검토 설명 (L3, F-06) | `03` R6·R7, US-05 | **섞인다** (사용자가 직접 쓴 글) | 가장 민감하다. 개인정보 결정 전에는 LLM에 보낼 수 없다 (R7) |

- 서술형 답변 자체는 사용자가 한국어로 쓴 글을 L3가 검토하는 구조다 (`03` 3-4 L3). 번역이 걸리는 부분은 검토 결과 설명을 모국어로 주는 것과, 사용자가 모국어로 쓴 초안을 한국어로 옮겨 주는 기능을 넣을 경우다. 후자는 현재 문서에 없다 `[추정]`. 넣을지는 `미정`이다.
- 번역 방식은 T-A·T-B에 거의 영향이 없고, T-C·T-D·T-E에서 갈린다. 특히 T-E의 개인정보 문제가 방식 선택의 핵심이다.

## 4. 방식별 설명

### 4-1. 방식 1. 번역 API

- 흐름: 서버가 한국어 문장을 번역 API에 보내고 모국어 결과를 받아 저장한다. T-A·T-B는 미리 번역해 저장하고, T-C는 실행 때 호출한다.
- 장점: 번역 품질이 안정적이고 응답이 빠르다. 구현이 가장 단순하다(HTTP 호출 한 번). 같은 입력에 같은 결과가 나온다. 문자 단위 과금이라 비용을 계산하기 쉽다.
- 단점: 문장을 옮길 뿐이다. "쉬운 한국어로 풀어 쓰기"(T-D)와 서술형 검토 설명(T-E)은 못 한다. 이 두 가지는 기존 L2·L3(Gemini)가 계속 맡아야 한다. 문맥이 없어서 공문서 용어(예: 수강료 감면 대상)가 어색하게 번역될 수 있다 `[추정]`. 외부로 텍스트가 나간다.
- 개인정보: 외부 서버로 나가므로 마스킹을 거친 텍스트만 보낸다. 공급자별 저장·학습 정책이 다르다(5절 표).

### 4-2. 방식 2. 번역 API + LLM

흐름 (역할 분담 `[제안]`):

| 대상 | 처리 |
| --- | --- |
| T-A, T-B | 번역 API로 한 번 번역 후 파일·DB에 저장, 통번역사 검수. LLM 미사용 |
| T-C | 번역 API로 번역. 번역이 부자연스러운 문장만 번역 LLM으로 다시 번역해 비교하는 선택 구간 |
| T-D | L2(Gemini 등 범용 LLM)가 쉬운 한국어 풀이를 만들고, 필요하면 모국어로 옮긴다 |
| T-E | 개인정보 차단 절차(4-2-2)를 모두 통과한 답변만 L3가 검토하고, 설명을 모국어로 만든다 |

#### 4-2-1. 번역 LLM 후보: `riva-translate-4b-instruct-v2`

| --- | --- | --- |

- 호스팅 API를 쓰면 텍스트가 NVIDIA 서버로 나간다. 마스킹 전제는 번역 API와 같다.

NVIDIA API Trial Terms(2025-09-19 버전)에 따르면 세션이 끝나면 저장하지 않는 것이 원칙이지만(2.3조), 서비스 제공업체를 통한 구독이 없으면 업로드 후 30일간 저장하고(2.4조), 입력과 생성 결과를 AI 모델을 포함한 제품 개선에 쓸 수 있으며(3.3조), 입력을 모니터링·검토할 수 있고(2.7조), 식별 가능한 개인의 개인정보 업로드를 금지한다(4.3조) `[사실]`. 모델 카드의 Privacy 항목은 사용자 입력을 학습에 쓰지 않는다고 적혀 있어 약관(3.3조)과 어긋나 보이며, 호스팅 서비스에는 약관이 적용된다. 마스킹이 끝난 양식 라벨·용어 사전처럼 개인정보가 없는 텍스트에만 쓸 수 있다.

#### 4-2-2. 서술형이어도 AI에 개인정보를 넘기지 않는 방법

핵심은 한 가지 방법으로 막지 않고 여러 겹으로 막는 것이다. 규칙(정규식)은 정해진 형태의 개인정보(전화번호, 이메일, 주민등록번호, 외국인등록번호)는 잘 잡지만, 이름·병명·학교 이름처럼 형태가 없는 정보는 못 잡는다. 이 한계 때문에 마지막 두 겹(사용자 결정, 로컬 경로)이 중요하다.

| 겹 | 방법 | 막는 것 | 못 막는 것 | 근거·위치 |
| --- | --- | --- | --- | --- |
| 1 | 서버 규칙(정규식)으로 개인정보 감지. 감지에 LLM을 쓰지 않는다 | 정해진 형식의 번호·이메일·주소 일부 | 이름, 병명, 학교 이름, 문장 속에 풀어 쓴 정보 | `DATA-MODEL.md` `privacy_detection` (R7) |
| 2 | 모달로 알리고 사용자가 `유지` / `삭제` / `검토 제외`를 정한다. 결정 전에는 답변 전체를 LLM과 번역 API에 보내지 않는다 | 1겹이 놓친 것 중 사용자가 알아본 것 | 사용자가 개인정보인지 모르고 지나간 것 | R7, F-07 |
| 3 | 보내는 글에서 감지된 부분을 토큰(`[PHONE_1]` 등)으로 바꿔 보내고, 응답이 오면 서버에서 되돌린다. 원문과 토큰의 대응표는 메모리에만 두고 저장하지 않는다 | 원문 값이 외부로 나가는 것 | 토큰이 번역 중 바뀌어 복원이 안 되는 경우. 복원 실패 시 해당 문장은 보내지 않고 사용자에게 알린다 | 4-2-3 |
| 4 | 보내기 직전 한 함수(발신 관문)에서 재검사한다. 번역 API·번역 LLM·범용 LLM으로 나가는 모든 호출이 이 함수만 통과하게 하고, 감지 결과가 비어 있지 않거나 결정 전이면 호출을 막는다 | 개발 중 실수로 마스킹을 건너뛰는 경로 | - | 저장소 루트 지침 문서 "한 함수에서 마스킹한 뒤에만", R1·R8 |
| 5 | 무료 티어 약관 확인. Gemini API 무료 티어(Unpaid Services)는 제출한 내용을 제품·ML 개발에 쓰고 사람이 입출력을 읽을 수 있으며, "민감·기밀·개인정보를 넣지 말라"고 원문에 적혀 있다 `[사실]`. 유료(Paid Services)는 프롬프트를 제품 개선에 쓰지 않는다고 적혀 있다 `[사실]` | 약관상 사람 검토 위험 | 외부 전송 자체 | 5-4 |
| 6 | 서술형(T-E)은 가능하면 서버로 보내지 않고 사용자 기기에서 처리한다 (방식 3의 로컬 번역을 서술형에만 적용) | 외부 전송 전체 | 로컬 환경이 안 되는 사용자 | 4-3 |
| 7 | 저장·로그 규칙: 감지된 원문은 저장하지 않고 위치(`start`, `end`)만 저장한다. 요청·응답 본문을 서버 로그와 캐시 키에 남기지 않는다(키는 해시). 서술형 임시 데이터는 처리 목적이 끝나면 삭제한다 | 서버 쪽 잔존 | - | R8, T4, `DATA-MODEL.md` |

- 남는 위험: 1~2겹을 지나도 "이름이 하나라도 가려지지 않은 채 남은" 경우(R8 예외 사례)는 규칙으로 100% 막을 수 없다 `[사실]`(규칙의 한계). 고객사 답변("이름 등 민감 정보가 있으면 절대 안 됨") 기준으로는 서술형 외부 전송이 가장 위험한 경로다.
- 그래서 `[제안]`: 서술형(T-E)은 (a) 사용자가 문장을 직접 확인한 뒤에만 보내는 방식(2겹)을 기본으로 하고, (b) 서버 전송 없이 처리하는 로컬 경로(6겹)를 우선 경로로 검토하며, (c) 두 경로가 모두 안 되면 서술형 설명의 모국어 번역은 이번 범위에서 빼는 것도 선택지로 둔다. 선택은 팀 투표 대상이다.

#### 4-2-3. 토큰 치환 시 번역 API별 주의 `확인 필요`

- 번역 중 토큰이 바뀌는 문제를 줄이려면 "번역하지 않음" 표시 기능이 필요하다. 공급자별 지원 방식은 공식 문서로 확인한다 `확인 필요`.
- 번역 LLM은 지시를 따르는 모델이라 토큰을 임의로 고치거나 풀어 쓸 수 있다 `[추정]`. 복원 검증(토큰 개수·순서 일치) 후 어긋나면 폐기하는 절차를 넣는다 `[제안]`.

### 4-3. 방식 3. 번역 API + 로컬 LLM

이 방식은 "서버 전송 없이 사용자 기기에서 번역"이 목적이다. 1단계 계획(팀이 작성한 내용)을 정리하고, 공식 문서와 대조한 결과를 붙인다.

#### 4-3-1. 1단계: 브라우저 내장 `Translator API` (ko, vi)

| 단계 | 내용 |
| --- | --- |
| 1. 지원 여부와 기기 상태 판별 | `'Translator' in self`로 지원 여부 확인. `Translator.availability({ sourceLanguage: 'ko', targetLanguage: 'vi' })`와 반대 방향(`vi`→`ko`)을 각각 조회해 상태 분기. 지원하지 않거나 `unavailable`이면 2단계로 넘어간다 |
| 2. 사용자 클릭 연동과 언어 팩 다운로드 UI | 첫 다운로드는 사용자의 버튼 클릭 안에서 `Translator.create()`를 호출. `monitor` 콜백의 `downloadprogress`로 진행률 표시. 설치가 끝나면 다음 방문부터 즉시 번역 |
| 3. 번역 실행과 인스턴스·UX 관리 | 짧은 글은 `translate()`, 긴 글은 `translateStreaming()`. `ko→vi`, `vi→ko` 인스턴스를 각각 만들어 재사용, 닫을 때 `destroy()`. 원문·번역문 토글, "서버 전송 없이 내 기기에서 번역됨" 배지 |
| 4. 로컬 환경 검증과 예외 처리 | Chrome·Edge 데스크톱에서 네트워크를 끊은 상태로 첫 다운로드 이후 번역이 되는지 확인. 저장 공간 부족·다운로드 실패 때 멈추지 않고 2단계로 넘어가는 `try-catch` |

공식 문서와 대조 (Chrome 개발자 문서 `translator-api`, `translate-on-device`):

| 항목 | 팀 계획 | 공식 문서에서 확인한 것 | 판정 |
| --- | --- | --- | --- |
| 지원 환경 | Chrome·Edge 데스크톱, Safari·Firefox·모바일은 제외 | Chrome 138, Edge 148에서 지원. Firefox·Safari 미지원. 모바일에서는 동작하지 않는다("These APIs don't work on mobile devices.") | 일치 `[사실]` |
| 언어 | `ko`, `vi` | 두 언어 모두 지원 목록에 있음. 목록은 Chrome 구현에 한정되며 바뀔 수 있다고 적혀 있음. `ko`↔`vi` 직접 언어쌍의 지원은 이 조사에서 확인하지 못함 | 언어는 일치, 언어쌍은 `확인 필요` |
| 사용자 클릭 필요 | 첫 다운로드는 클릭 안에서 `create()` | `create()` 호출 전에 사용자 활성화를 확인해야 한다고 적혀 있음. 세부 조건은 별도 페이지 | 일치 `[사실]` |
| 진행률 | `monitor`의 `downloadprogress` | `downloadprogress` 이벤트로 진행률 확인. 실패하면 이벤트가 멈추고 `ready` promise가 거부됨 | 일치 `[사실]` |
| 긴 글 | `translateStreaming()` | 긴 텍스트에 `translateStreaming()` 사용 가능. 번역은 순차 처리라 큰 입력은 뒤 요청이 대기하므로 나눠 보내라고 권장 | 일치 `[사실]` |
| `availability()` 상태 4가지 | `available`, `downloadable`, `downloading`, `unavailable` | 확인한 문서에는 `downloadable`, `available`만 나온다. 언어쌍별 다운로드 상태는 개인정보 보호를 위해 숨겨져, 사이트가 번역기를 만들기 전까지 모두 `downloadable`로 보고된다고 적혀 있음 | 4가지 값은 `확인 필요`. 위 개인정보 보호 동작은 설계에 반영해야 함 |
| "RAM 16GB 미만이면 `unavailable`" | 1단계 건너뜀 조건으로 사용 | 22GB 여유 공간, RAM 16GB 이상, VRAM 4GB 초과 같은 수치는 Prompt·Summarizer·Writer·Rewriter·Proofreader API 기준으로 적혀 있고, Translator 전용 수치는 찾지 못함 | 근거 없음 `확인 필요`. 이 조건으로 분기하지 않는다 |
| 구버전 `window.ai.translator` | 사용하지 않음 | 이번 조사에서 직접 확인하지 못함 | `확인 필요` |
| Web Worker | 언급 없음 | Web Worker에서는 쓸 수 없음. cross-origin iframe은 `allow="translator"` 필요 | 구현 시 주의 `[사실]` |
| 개인정보 | "서버 전송 없이" 배지 | 모델 사용 시 Google이나 제3자에 데이터가 전송되지 않고, 네트워크는 최초 모델 다운로드에만 필요하다고 on-device 문서(Prompt 계열 설명)에 적혀 있음. Translator에 대한 같은 문구는 직접 확인하지 못함 | Translator에 대해서는 `확인 필요`. 배지 문구는 확인 뒤 사용 |
| 번역 품질 | - | "high-quality"라는 설명만 있고 품질 수치는 없음 | 품질은 우리가 직접 평가해야 함 |

- 팀 계획의 "4가지 상태"와 "RAM 16GB 미만"은 확인 가능한 공식 근거를 찾지 못했다. 설계에서는 상태 이름에 의존하지 말고, `Translator` 존재 여부, `availability()`가 던지는 오류, `create()` 실패를 모두 폴백 신호로 처리하는 편이 안전하다 `[제안]`.
- 시연이 각자 Mac의 Chrome이면 1단계 조건(Chrome 138 이상, 데스크톱)은 충족할 가능성이 높다 `[추정]`. 버전은 각자 확인한다 `확인 필요`.
- 사용자(결혼이민자)의 실제 기기가 휴대폰이면 1단계는 거의 못 쓴다. 사용자 기기 분포는 모른다 `미정`(고객사 질문 후보).

#### 4-3-2. 2단계 폴백: `Transformers.js`

- 브라우저에서 번역 모델을 직접 돌리는 방식(2단계)이다. 이 조사에서는 확인하지 않았다 `확인 필요`: 한국어↔베트남어 지원 모델 존재 여부, 모델 크기와 첫 다운로드 시간, 모바일 동작, 번역 품질, 라이선스. 도입을 결정하기 전에 위 다섯 가지를 먼저 확인해야 한다.
- 로컬 번역 모델은 일반적으로 서버 번역 API보다 품질이 낮고 첫 다운로드가 크다 `[추정]`.

#### 4-3-3. 번역 LLM을 로컬에서 돌리는 경우 (`riva-translate-4b-instruct-v2` 자체 구동)

- 모델 카드에 양자화 모델과 llama.cpp·Ollama·LM Studio 호환이 안내돼 있다 `[사실]`. 각자 Mac에서 서버 쪽으로 돌려 서버 번역 경로의 "로컬 대체"로 쓰는 구성이 가능하다 `[추정]`.
- 모델 카드의 테스트 환경은 데이터센터급 GPU이고 최소 사양은 없다. Apple Silicon(팀 시연 환경)에서의 메모리·속도는 직접 돌려 보기 전에는 모른다 `확인 필요`.
- 이 경우 외부 전송이 없어 개인정보 위험은 가장 낮지만, 사용자 PC가 아니라 서버(시연 때는 각자 Mac)에서 돌기 때문에 서비스를 배포하면 서버 쪽 GPU·메모리 부담이 생긴다 `[추정]`.

### 4-4. 로컬 LLM 방식이 어려운 이유 `[제안]`

방식 3(브라우저 내장 번역, `Transformers.js`, 모델 자체 구동)의 장점은 서버 전송이 없다는 점이다. 그러나 아래 이유로 번역 기능 전체의 기본 방식으로 쓰기는 어렵다고 본다. 근거가 공식 문서로 확인된 것과 추정인 것을 구분해 적는다.

| 번호 | 이유 | 근거 | 태그 |
| --- | --- | --- | --- |
| 1 | 지원 환경이 좁다. 브라우저 내장 `Translator API`는 Chrome 138, Edge 148의 데스크톱에서만 되고, 모바일과 Firefox·Safari에서는 안 된다. 대상 사용자(결혼이민자)의 기기 분포를 모른다 | 4-3-1 대조표, Chrome 개발자 문서 | `[사실]` / 기기 분포 `미정` |
| 2 | 1단계가 안 되는 환경의 폴백이 비어 있다. `Transformers.js`로 `ko`↔`vi`를 지원하는 모델, 크기, 첫 다운로드 시간, 모바일 동작, 품질, 라이선스를 하나도 확인하지 못했다. 폴백이 확정되지 않으면 결국 서버 번역 경로가 하나 더 필요해, 로컬만으로 끝나지 않고 구현 경로가 2~3개로 늘어난다 | 4-3-2 | `확인 필요` |
| 3 | 분기 조건의 근거가 부족하다. `availability()`의 4가지 상태와 "RAM 16GB 미만이면 `unavailable`" 조건은 공식 문서에서 확인하지 못했다. 언어쌍별 다운로드 상태는 개인정보 보호를 위해 숨겨져 `downloadable`로만 보고된다고 적혀 있어, 상태를 미리 보고 분기하는 설계가 어렵다 | 4-3-1 대조표 | `[사실]` / `확인 필요` |
| 4 | 구현 제약이 있다. 번역이 순차 처리라 긴 입력은 뒤 요청이 대기하고, Web Worker에서 쓸 수 없으며, cross-origin iframe은 `allow="translator"`가 필요하다. 첫 사용에는 사용자 클릭 안에서 언어 팩을 내려받아야 해 다운로드 진행·실패 화면이 따로 필요하다 | Chrome 개발자 문서 | `[사실]` |
| 5 | 번역 품질 근거가 없다. 공식 문서는 "high-quality"라고만 하고 수치가 없다. 공문서 용어(예: 수강료 감면 대상)에서 얼마나 정확한지는 직접 평가해야 한다 | 4-3-1 대조표 | `[사실]` (수치 없음) |
| 6 | 결과가 기기·브라우저 버전마다 달라질 수 있어 시연과 테스트 재현이 어렵다. `STACK.md`의 "테스트·실행 재현" 항목과 맞지 않는다 | `STACK.md` | `[추정]` |
| 7 | 모델을 직접 구동하는 방식(`riva-translate-4b-instruct-v2` 등)은 사양 근거가 없다. 모델 카드의 테스트 환경은 A100, H100 80GB, Jetson Thor, DGX Spark이고 최소 VRAM은 적혀 있지 않다. 4B 파라미터 BF16이면 가중치만 약 8GB다(4 x 10^9 x 2바이트 계산). 양자화 모델의 크기와 Apple Silicon에서의 속도는 확인하지 못했다 | 4-2-1, 4-3-3 | `[사실]` / 계산 / `확인 필요` |
| 8 | 시연은 각자 Mac에서 하는데 OCR(PaddleOCR 또는 EasyOCR, arm64 동작 미확인), FastAPI, Vite 개발 서버가 이미 메모리를 쓴다. 여기에 번역 모델까지 올리면 자원 경쟁이 생길 수 있고, 모델은 각자 Mac에서 따로 내려받아야 한다 | `STACK.md` 예상 어려움 표 | `[추정]` |
| 9 | 팀 조건과 맞지 않는다. 개발 기간이 "8주" 또는 "15시간"으로 문서마다 다르고, React를 처음 쓰는 팀원이 있다. 방식 3은 환경 판별, 다운로드 UI, 인스턴스 관리, 폴백 분기, 브라우저별 테스트까지 프론트 작업이 크다. 서버에서 API를 한 번 호출하는 방식은 FastAPI만으로 끝난다 | `STACK.md`, `PRD.md` 8절 | `[사실]` (문서 기록) |

- 정리: 로컬 방식은 개인정보 위험이 가장 낮다는 장점이 있지만, 지원 환경(1), 비어 있는 폴백(2), 확인되지 않은 조건(3, 7), 구현량(9) 때문에 이번 범위의 기본 방식으로는 부담이 크다 `[제안]`.

### 5-2. 선택과 변경 이력 `[제안]`

> 보류: 이후 Google Cloud Translation도 체험판만 있고 결제 수단이 필요한 점을 확인해, 번역 구간은 Groq API로 바꿨다(5-5절). 아래 내용은 변경 이력으로 남긴다.

- 처음 제안(1순위 Azure AI Translator F0, 2순위 Google Cloud Translation)은 팀이 확인한 사실로 바뀌었다. Azure는 가입 때 카드 정보를 요구해 제외한다.
- 보류(당시 선택): **Google Cloud Translation Basic (v2) 체험판**. 당시 이유: `ko`, `vi` 지원을 확인했고, 입력 내용을 번역 기능 개선 학습에 쓰지 않는다고 명시돼 있으며, 체험 중에는 과금되지 않는다.
- 정정: 앞서 "월 50만 자 무료"라고 적은 것은 가격 페이지 표기였다. 이 한도가 카드 없이 쓰는 상시 무료인지는 확인되지 않았고, 계정 요건을 확인해 보니 체험판 가입에도 결제 수단이 필요하다 `[사실]`. 즉 Azure와 마찬가지로 Google도 카드 정보를 요구한다. 팀이 Azure를 뺀 이유(카드 요구)가 Google에도 해당하는지는 팀이 판단한다.
- 체험판 조건 (공식 Free Trial 안내 `[사실]`):
  - $300 크레딧, 가입 후 90일간 유효. 크레딧을 다 쓰거나 90일이 지나면 체험 결제 계정이 닫힌다.
  - 체험 중에는 과금되지 않고, 종료 후에도 직접 유료로 업그레이드하지 않으면 청구되지 않는다. 업그레이드하지 않으면 리소스가 멈추고 30일 유예 뒤 삭제된다.
  - 유료 업그레이드는 하지 않는다 (`STACK.md` "비용: 무료만" 유지).
  - Cloud Translation이 $300 크레딧 대상인지는 이번에 확인하지 못했다. 대부분의 서비스에 적용되는 것으로 알려져 있으나 `[추정]`, 가입 뒤 청구 화면에서 확인한다 `확인 필요`.
- 비교 후보로만 두기: Papago, DeepL (확인하지 못한 항목은 5-1 표 참고).
- 정하는 방법: 같은 샘플 문장 20~30개(신청서 칸 라벨, 용어 사전 설명 일부)로 `ko→vi` 번역 품질을 확인하고, 통번역사나 베트남어를 아는 사람이 점수를 매긴다 `[제안]`. 품질은 공개 수치로 정하지 않는다.

### 5-3. 사용량과 체험 기간 대응 `[가정]`

- 번역 API 호출량 = (문서 한 건의 번역 대상 글자 수) x (언어 수) x (작성 건 수). 정적 문구(T-A, T-B)는 한 번만 번역해 저장하므로 실행 때 호출량에서 빠진다.
- 체험 크레딧으로 보는 상한: Basic 가격이 100만 자당 $20이므로 $300은 계산상 약 1,500만 자다 (300 / 20 x 100만). 크레딧이 번역에 적용된다는 `확인 필요`를 전제로 한 계산이다.
- 예시 가정(팀이 실제 값으로 바꾼다): 항목 설명 30개 x 평균 40자 = 1,200자, 언어 3개면 한 건당 3,600자. 이 가정의 숫자는 근거가 없는 예시다. 개발·테스트 규모에서는 크레딧이 모자랄 가능성이 낮다 `[추정]`.
- 진짜 문제는 금액이 아니라 기간(90일)이다. 대응 `[제안]`:
  1. 가입일과 종료 예정일을 기록한다. 종료 뒤에는 번역 호출이 안 된다.
  2. 정적 문구(T-A, T-B)와 시연에 쓸 항목 설명은 체험 기간 안에 번역해 파일·DB에 저장하고, 통번역사 검수까지 마친다.
  3. 실행 때 번역은 저장된 결과를 먼저 쓰고 없을 때만 API를 부른다(양식 버전·언어를 키로 캐시). 체험이 끝나면 캐시만으로 시연한다.
  4. 90일 이후에도 새 문서를 번역해야 하면, 그때 방식 3(브라우저 내장 번역)으로 바꾸거나 다른 공급자를 고른다 `미정`.
- API 키는 `.env`에만 두고 저장소에 올리지 않는다. 팀원 각자 Mac에서 쓰려면 키를 어떻게 나눌지(한 계정의 키를 공유할지) 정해야 한다 `미정`. 공유하면 호출량이 한 계정에 합산된다.

### 5-5. 제안: Groq API `[제안]` `[팀 확정 전]`

번역 구간에 Groq API를 쓰자고 제안한다. 결정은 팀 투표로 한다. 이 제안은 번역 기능에 한한다. L1~L3(입력 항목 추론, 쉬운 풀이, 서술형 검토)를 Gemini로 계속 할지 Groq로 옮길지는 `STACK.md`에 적힌 결정이라 이 문서에서 바꾸지 않는다 `미정`.

제안 이유:

1. 카드: 가입 때 카드가 필요한지는 아직 확인하지 못했다 `확인 필요`. 콘솔에서 API 키 발급까지 마친 화면은 확인했지만, 그 화면만으로는 가입 때 카드를 입력했는지 알 수 없다. 공식 문서에는 무료 플랜의 카드 요구가 적혀 있지 않고, 결제 수단은 Developer 플랜 업그레이드 때만 필요하다고 적혀 있다 `[사실]`(문서 기재 내용에 한함). 이 점이 확인되면 Azure·Google과 다르다.
2. 데이터 취급: 기본은 비보관이고 Zero Data Retention을 켤 수 있다 `[사실]`. Gemini 무료 티어(사람 검토 가능)와 NVIDIA Trial(30일 저장, 제품 개선 사용 가능)보다 약관상 부담이 작다.
3. 구현: FastAPI 서버에서 API를 한 번 호출하는 방식이라 `STACK.md`의 "LLM은 서버에서만 호출" 규칙과 맞고, 로컬 방식(4-4절)보다 구현량이 작다.
4. 한도: 정적 번역(용어 사전, 화면 문구, 양식별 항목 설명)은 결과를 저장해 재사용하므로 하루 1,000회 한도 안에서 운영할 수 있다 `[추정]`.

한계와 주의:

- 번역 전용이 아니므로 `ko`↔`vi` 품질은 샘플 문장 20~30개로 직접 평가한다(통번역사 또는 베트남어를 아는 사람 검수) `[제안]`.
- 후보 모델: `openai/gpt-oss-120b`(프로덕션), `openai/gpt-oss-20b`(프로덕션). `qwen/qwen3.8-27b`는 프리뷰라 프로덕션에 쓰지 않는다. `llama` 계열은 "Enterprise" 표시라 무료로 쓸 수 있는지 `확인 필요`. 기본 후보는 `gpt-oss-120b` `[제안]`이고 품질 평가로 정한다. 모델명은 `.env`로 분리한다.
- 한도가 조직 단위이고 분당 8K 토큰이라, 여러 팀원이 키를 같이 쓰면 합산된다. 추론 과정을 쓰는 모델은 출력 토큰이 늘어 한도에 빨리 닿을 수 있다 `[추정]`. 문장을 묶어서 한 번에 호출하는 방식을 검토한다 `[제안]`.
- 한도 초과 시 429 오류와 `retry-after` 헤더가 온다 `[사실]`. 저장된 번역을 먼저 쓰고, 429가 오면 저장 결과로 대체하거나 대기한다.
- 학습 사용 여부와 서비스 약관의 개인정보 입력 조항은 확인하지 못했다. 서술형 같은 사용자 입력을 보내기 전에 약관을 먼저 확인한다 `확인 필요`.
- 데이터가 미국에 보관된다 `[사실]`.
- 무료 플랜의 조건은 바뀔 수 있으므로 도입 전과 시연 전에 콘솔 limits 페이지를 다시 확인한다.

| 1 | 콘솔 Data Controls에서 Zero Data Retention을 켜는 것을 제안한다. 켜면 장애·남용 조사용 임시 로그도 보관하지 않는다 |
| 2 | API 키는 `.env`에만 두고 저장소에 올리지 않는다. 변수 이름은 팀이 정한다 `미정` |
| 3 | Groq 호출은 4-2-2의 발신 관문 함수 하나만 통과하게 한다. 감지 결과가 비어 있지 않거나 결정 전이면 호출하지 않는다 |
| 4 | 응답은 양식 버전·언어를 키로 저장해 재사용한다. 요청·응답 본문은 서버 로그에 남기지 않는다 |
| 5 | 콘솔 limits 페이지에서 실제 한도를 확인하고 이 문서 5-4절 표를 고친다 |

번역 대상별 적용 `[제안]`:

| 대상 | Groq 사용 방식 |
| --- | --- |
| T-A, T-B | 미리 번역해 저장하고 통번역사가 검수한다. 실행 때는 호출하지 않는다 |
| T-C | 마스킹이 끝난 칸 라벨만 보낸다. 같은 양식은 저장 결과를 재사용한다 |
| T-D | 쉬운 한국어 풀이와 모국어 번역을 만든다. 입력은 단어·문장과 사전 설명뿐이다 |
| T-E | 4-2-2의 7겹을 모두 통과한 답변만 보낸다. 서술형 외부 전송이 부담되면 이번 범위에서 빼거나 지원 브라우저에서 선택적으로 로컬 처리한다(4-4절) `미정` |

### 6-2. 어떤 경우에 어느 방식이 맞나 (판단 도움)

| 상황 | 가까운 방식 | 이유 |
| --- | --- | --- |
| 용어 사전·화면 문구·오류 메시지 번역 (T-A, T-B) | 방식 1 | 한 번 번역하고 검수해 저장. LLM이나 로컬 모델을 쓸 이유가 약함 |
| 문서마다 달라지는 항목 설명 (T-C) | 방식 1 (품질이 부족하면 방식 2 보완) | 라벨 같은 짧은 문장 위주라 번역 API로 시작해 보고, 어색한 문장이 많으면 그때 LLM 추가 |
| 쉬운 풀이 (T-D) | 기존 L2(범용 LLM) | 번역이 아니라 쉽게 바꾸는 일이라 번역 API나 번역 전용 모델로는 부족 |
| 서술형 검토 설명 (T-E) | 방식 3(로컬) 또는 방식 2의 1~7겹 | 외부 전송을 줄이는 쪽이 고객사 기준에 안전. 둘 다 어려우면 이번 범위에서 제외 검토 |

## 7. 이 문서의 한계

- 번역 품질은 공식 문서에 수치가 없거나(`Translator API`) 영어 쌍만 있다(`riva-translate`). 한국어↔베트남어 품질 비교는 직접 만든 샘플 평가로만 말할 수 있다.
- 가격과 한도는 2026-11-17에 확인한 값이다. 도입 직전에 다시 확인한다.
- 팀 계획의 1단계(`Translator API`)에서 공식 문서로 확인하지 못한 항목(4가지 상태, RAM 16GB 조건, 구버전 API 중단)은 근거가 확인될 때까지 `확인 필요`로 둔다.
- 2단계 폴백(`Transformers.js`)은 이번 조사에서 확인하지 않았다.
- Groq의 한도 표는 무료 플랜과 Developer 플랜 중 어느 쪽 수치인지 문서상 모호하다. 모델별 한국어·베트남어 품질은 공식 자료로 확인하지 못했다. 학습 사용 여부와 서비스 약관의 개인정보 조항도 확인하지 못했다.
- 5-4절의 후보 조사는 공식 문서의 요약 확인에 근거한다. 약관류(NVIDIA API Trial Terms)는 원문을 직접 한 번 더 읽고 확인해야 한다.
