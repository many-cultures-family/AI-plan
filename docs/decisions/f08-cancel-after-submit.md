# F-08 제출 후 작성 건 취소 허용 여부

- 작성일: 2026-11-10
- 결정 방법: 팀 투표 (`docs/team/working-agreement.md` 기준)

## 결정

**A안 채택** — 제출(`submitted_at` 기록) 후에도 작성 건 취소를 허용한다. `수정`·`반려`·`성공` 어느 상태에서든, 제출 여부와 관계없이 취소할 수 있다.

## 왜 투표가 필요했나

`docs/domain/03-rules-states-llm.md` 79행과 `docs/DATA-MODEL.md` 123행은 "`수정`·`반려`·`성공` → `취소`"라고만 적고 제출 여부 조건이 없다. 반면 `docs/requirements/backlog.md`는 US-07 본문·172행·198행에서 반복해서 "제출 전"을 전제로 깔고 있었다(제안서 Ⅳ-12 근거). 두 문서군이 서로 다른 전제를 쓰고 있어 팀 결정이 필요했다. 이 충돌은 `docs/api/DRAFT-STATUS-API.md`(F-08 API 명세, PR #109) 리뷰 중 발견됐다.

## 후보와 근거

| 안 | 내용 | 근거 |
| --- | --- | --- |
| **A (채택)** | 제출 여부와 관계없이 모든 상태에서 취소 가능 | 제출(R10)은 기록으로만 남고 상태를 바꾸지 않으므로 제출한 작성 건도 여전히 `성공`이다. 제출 후 취소를 막으면 사용자가 업로드 파일·입력값을 지울 방법이 없어져 개인정보 보호법 제21조(목적 달성 후 파기)·R8·T3 취지와 어긋난다 |
| B | US-07 원문대로 제출 전에만 취소 가능, 제출 후엔 `409 ALREADY_SUBMITTED`로 거절 | `backlog.md`·제안서 Ⅳ-12 원문과 그대로 일치 |

## 주의할 것

제출 후의 "취소"는 실제 신청 취소가 아니라 "이 서비스에 남은 연습 데이터 삭제"다. 공식 사이트에 낸 신청 자체는 이미 끝난 일이라 되돌릴 수 없다. 화면 문구에서 이 둘을 구분하지 않으면 사용자가 실제 신청이 취소됐다고 오해할 수 있다 — F-08 프론트 담당이 화면 문구 설계 시 반영한다.

- `docs/api/DRAFT-STATUS-API.md` 항목 3 — A안대로 수정 완료 (PR #109)
