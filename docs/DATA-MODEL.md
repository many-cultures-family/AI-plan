# 데이터 구조

> **저장 위치:** `docs/DATA-MODEL.md`

> **사용 방법**
> 1. PRD의 '데이터 구조'를 **확정**하는 문서입니다. PRD와 다르게 쓰지 않고, 확정한 내용을 PRD에도 옮깁니다.
> 2. **상태값은 `docs/domain/03-rules-states-llm.md`의 상태와 똑같이** 씁니다. 이름이 다르면 나중에 테스트가 어긋납니다.
> 3. 모델마다 **핵심 필드 3~5개**부터 시작합니다. 필드를 많이 만들지 않습니다.
> 4. Claude는 빠진 필드와 모순을 **찾아 주기만** 합니다. 어떤 필드를 둘지는 팀이 정합니다.
> 5. 시드(예시) 데이터 3~5건은 오늘 만드는 기능의 화면 확인에 쓰고, 다음 시간 테스트 입력으로도 씁니다.
> 6. **개발자1이 씁니다.** 결정은 팀이 하고, 파일에 적는 것은 개발자1(공유 파일이라 PM이 PR로 올림)입니다.
> 7. `>`로 시작하는 안내 문장은 지워도 됩니다.

- 상태: **초안 (Claude 작성, 팀 확정 전)** — 로그인 방식(Google 로그인만 지원)은 팀원이 정했다. 나머지 설계 세부는 규칙(R1~R12, T3·T4)·인수 조건과 보편적인 방식에 맞춰 Claude가 채웠다. 그중 고객 답변이 필요하거나 다른 문서와 어긋나는 값에는 `[제안]`을 붙였다
- 확정일:
- 근거: `PRD.md`, `03-rules-states-llm.md`(3-1 R1~R12, 3-2 상태, 3-3 T1~T4, 3-4 L1~L3), `backlog.md`(US-01~US-07), `mvp-scope.md`, `client-meeting-1.md`, 제안서 v2 Ⅳ-11(F-01~F-08)·Ⅳ-13(L1~L3)

> 필드 이름은 코드에서 그대로 쓸 영어 snake_case입니다. 상태값(`draft.status`)만 `03` 문서와 같은 한국어 문자열로 저장합니다.
> 타입은 ORM이 정해지지 않아 일반 이름으로 씁니다: 정수 / 문자열 / 참거짓 / 날짜시간 / JSON(문자열로 저장).

- LLM이 만든 값은 `form_field`(L1), `easy_explanation`(L2), `review_suggestion`(L3)에만 저장한다. `form_field`는 사용자가 확인해야 확정되고(`draft.fields_confirmed_at`), `easy_explanation`은 'AI 풀이'로 표시만 하며 상태를 바꾸지 않고, `review_suggestion`은 사용자가 고른 것만 반영한다(`decision`).
- 사전 정보와의 불일치는 **저장하지 않는다.** 규칙 엔진이 입력값을 저장하거나 화면을 열 때마다 `prior_info.value`와 비교해 계산하고, 차이 나는 글자는 화면에서 표시한다. 그래서 사전 정보를 고쳐도(R11) 낡은 판정이 남지 않는다 (R3).
- 마스킹 전 OCR 원문은 **저장하지 않는다.** OCR 결과를 메모리에서 바로 가려 `masked_text`로만 저장한다 (R8 최소 수집). `STACK.md`의 "원문은 서버 DB에만 저장"과 다르며, 원본 파일(`file_path`)은 화면 표시를 위해 취소 전까지 둔다.
- 서술형 검토용 임시 데이터(`review_suggestion`, `privacy_detection`)는 작성 건이 `성공` 또는 `취소`가 되면 지운다 (T4 "처리 목적 달성 시점").
- 신청 마감일 필드는 두지 않는다 (`mvp-scope.md` "마감일은 다루지 않음"을 따름. `03` T1과 다름).
- 상태 변경 기록(누가·언제·어느 상태에서 어느 상태로)은 DB 테이블을 두지 않고 서버 로그로 남긴다 (미팅1 질의응답 3 "로그로만 남기기").
- `form_field`는 안내 3의 "핵심 필드 3~5개"보다 많은 10개다. 필드마다 쓰는 인수 조건·규칙을 설명 칸에 적었다.

## 관계
> 모델 사이 연결을 한 줄씩. 예) 신청 → 글 (신청은 글 하나에 속한다)
- 사용자 → 작성 건 (사용자 한 명이 작성 건 여러 개를 가진다)
- 사용자 → 사전 정보 (사용자 한 명이 사전 정보 종류마다 1개를 가진다. 여러 작성 건이 같이 쓴다, R11)
- 작성 건 → 업로드 문서 (작성 건 하나에 업로드 문서 하나. 재업로드는 교체)
- 작성 건 → 입력 항목 (작성 건 하나에 입력 항목 여러 개)
- 입력 항목 → 입력 형식 (입력 항목은 허용 목록의 형식 하나를 쓴다)
- 입력 항목 → 사전 정보 (`prior_info_key`로 같은 사용자의 사전 정보 하나와 비교한다. 연결이 없을 수 있다)
- 입력 항목 → 입력값 (입력 항목 하나에 입력값 0~1개)
- 입력값 → 개인정보 감지 (서술형 입력값 하나에 감지 결과 0개 이상)
- 입력값 → 검토 제안 (서술형 입력값 하나에 검토 제안 여러 개)
- 쉬운 풀이 → 용어 사전 (쉬운 풀이는 용어 사전 단어 하나에 속하거나, 사전에 없는 단어면 속하지 않는다)

## 상태값 (핵심 대상의 `status`)

| 상태값 | `03` 문서의 상태 이름 | 누가 바꿀 수 있나 | 어떤 경우에 바뀌나 |
| --- | --- | --- | --- |
| `수정` | 수정 | 사용자 | 문서를 올려 작성 건이 생길 때(처음 상태), `반려`에서 재업로드·재분석 요청·입력 수정을 시작할 때, `성공`에서 제출 전에 다시 고칠 때나 쓰던 사전 정보를 고칠 때(R11) |
| `반려` | 반려 | 시스템 (규칙 엔진) | `수정`에서 OCR 인식 실패·페이지 누락(R1), 입력 항목 규칙 검증 실패(R2), 성공 조건이 남은 채 완성 요청(R9) 중 하나. `reject_reason`에 사유 코드를 남긴다 |
| `성공` | 성공 | 시스템 (규칙 엔진) + 사용자 | `수정`에서 필수 항목 모두 입력, 불일치 0개 또는 사용자가 차이 확인, 검토 제안 모두 결정, 개인정보 결정 완료(R9)를 규칙 엔진이 확인하고 사용자가 완성본을 최종 확인할 때 |
| `취소` | 취소 | 사용자 | `수정`·`반려`·`성공`에서 작성 포기를 고를 때. 다시 열지 않고, 다시 쓰려면 새 작성 건을 만든다 (R12). `draft` 행은 `취소` 상태로 남겨 작성 목록에서 숨기고, 업로드 문서·입력 항목·입력값·검토 제안·감지 결과는 지운다 (T3, US-07) |

- 취소·반려 경로로 가는 상태: `수정` → `반려`(R1·R2·R9), `반려` → `수정`(사용자 재시작), `성공` → `수정`(다시 고치기·R11), `수정`·`반려`·`성공` → `취소`(R12, 되돌릴 수 없음)
- LLM이 상태를 **직접 바꾸지 않고**, 사람이나 규칙이 최종 결정하는 곳:
  - L1 입력 항목 추론: 결과는 `form_field`에 제안으로만 저장한다. 규칙 검증에 실패하면 규칙 엔진이 `03` R2·3-2대로 `반려`(`FIELD_INVALID`)로 바꾸고, 확정(`fields_confirmed_at`)은 사용자가 한다 (R2) `[제안]` — `backlog.md` US-02·US-03 인수 조건은 실패 때 머문다고 적혀 있어 팀이 맞춰야 한다
  - L2 쉬운 풀이: 상태를 바꾸지 않는다 (`수정` 유지)
  - L3 서술형 검토: 제안의 `decision`은 사용자만 바꾼다 (R6). `성공`은 규칙 엔진의 R9 확인과 사용자의 최종 확인으로만 바뀐다
  - 오류 판정(필수 누락·형식 오류·사전 정보 불일치)은 규칙 엔진만 한다 (R3)

## LLM에 보내지 않을 정보
> 제안서 Ⅳ-13과 `03` 문서에서 가져옵니다. 이 필드는 LLM 호출 입력에 포함하지 않습니다.

| 모델 | 필드 | 보내지 않는 이유 |
| --- | --- | --- |
| 사전 정보 `prior_info` | `value` | 사전 정보 원본은 LLM에 보내지 않는다 (R8, `03` 3-4 L2·L3, US-04) |
| 업로드 문서 `document` | `file_path`(원본 파일), 마스킹 전 OCR 텍스트 | 문서에 적힌 이름·주민등록번호·외국인등록번호·연락처는 가린 뒤에만 보낸다. L1에는 `masked_text`, `bbox`, 라벨, 사용 언어만 보낸다 (R1, L1). 이미지를 LLM에 직접 넣지 않는다 (`mvp-scope.md` 제외 표) |
| 입력값 `field_answer` | `value` (L1·L2) | L1·L2 입력에는 사용자가 쓴 값이 없다 (`03` 3-4 L2) |
| 입력값 `field_answer` | `value` 중 `privacy_detection.decision`이 비어 있는(결정 전) 답변 전체, `삭제`·`검토 제외`로 정한 부분 | 개인정보 결정 전이거나 사용자가 보내지 않기로 한 내용 (R7, L3) |
| 사용자 `user` | `id`, `google_sub`, `email` | 작성에 필요한 범위가 아님 (R8) |
| (저장 안 함) | 인증번호·비밀번호, Google 토큰 | 받지도 저장하지도 않는다 (R8) |
